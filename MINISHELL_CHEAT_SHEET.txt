MINISHELL — CHEAT SHEET (mode soutenance 42, version impitoyable)
Date: 15/02/2026

============================================================
1) FLUX D’EXÉCUTION VULGARISÉ (de la ligne saisie à l’exécution)
============================================================

1. Readline récupère la commande utilisateur (`shell_loop`).
2. Tokenization: la string est découpée en tokens chaînés (`t_token`) : mots, pipes, redirections (`tokenize*`).
3. Expansion: sur les `WORD`, le shell gère quotes + `$VAR` + `$?` (`expand_*`).
   - `'...'` => pas d’expansion
   - `"..."` => expansion autorisée
   - non quoté / mixte => expansion morceau par morceau
4. Parsing: les tokens deviennent une liste de commandes (`t_cmd`), une commande par segment de pipeline (`parse_*`).
   - Vérification de syntaxe (`|` mal placé, redirection sans cible, etc.)
   - Construction de `args`, `infile`, `outfile`, `heredoc`
5. Heredoc préparés avant exécution (`prepare_heredocs`): chaque heredoc est lu, stocké dans un pipe, puis attaché au `t_cmd` via `heredoc_fd`.
6. Dispatch exécution (`execute_commands`):
   - 1 seule commande builtin => exécutée dans le parent (pour modifier l’état shell)
   - sinon pipeline => fork des enfants + connexions pipes + exec/builtin côté enfant
7. Attente des enfants (`waitpid`) et mise à jour de `g_exit_status`.
8. Libération mémoire de la ligne courante (`tokens`, `cmds`), puis boucle suivante.

Mini vision mentale:
input -> tokens -> expansion -> cmds -> heredoc fd -> exec (builtin/external/pipe) -> wait -> g_exit_status


============================================================
2) STRUCTURES DE DONNÉES PRINCIPALES (et pourquoi elles existent)
============================================================

A) `t_token`
- Champs: `value`, `type`, `next`.
- Rôle: représentation linéaire de la ligne utilisateur, avant parsing final.
- Cycle mémoire: alloué pendant tokenization, éventuellement modifié par expansion, puis libéré par `free_tokens`.

B) `t_cmd`
- Champs:
  - `args` : argv prêt pour builtin/execve
  - `infile`, `outfile`, `append` : redirections
  - `heredoc`, `heredoc_fd` : delimiter puis FD réel
  - `redir_error` : drapeau d’erreur de redirection
  - `next` : pipeline chaîné
- Rôle: unité d’exécution (une commande logique) utilisée par exec.
- Cycle mémoire: créé au parsing, enrichi par heredoc prep, consommé par l’exécution, libéré par `free_commands`.

C) `t_pipe_data`
- Champs: `cmds`, `env`, `count`, `pipes`, `pids`.
- Rôle: contexte runtime pour exécuter un pipeline multi-process.
- Cycle mémoire: alloué dans `execute_pipes`, utilisé pendant fork/wait, libéré juste après.

D) `char **env`
- Rôle: environnement shell mutable.
- Cycle mémoire: copie profonde au démarrage (`copy_env`), modifiée par `export/unset/cd`, libérée à la fin (`free_env`).

E) `g_exit_status`
- Rôle: état global de retour, lu par `$?` et écrit par erreurs/signaux/wait/builtins.
- Important soutenance: il est la “source de vérité” du status shell entre 2 prompts.

4) 5 QUESTIONS PIÈGES TECHNIQUES (avec réponses basées sur TON code)
============================================================

Q1) Pourquoi une redirection `>` peut déjà créer/tronquer un fichier avant même l’exécution réelle ?
R: Dans `parse_redir.c`, `handle_output_redir` fait un `open(... O_TRUNC/O_APPEND ...)` pendant le parsing pour détecter les erreurs de permission, puis ferme immédiatement. Le fichier peut donc être impacté très tôt, avant fork/exec.

Q2) Dans `export X=1 | cat`, pourquoi `X` ne reste pas dans l’environnement du shell ?
R: En pipeline, chaque maillon est forké (`exec_pipe_run.c`) et les builtins du pipeline tournent côté enfant (`pipe_child_exec`), donc les modifications d’environnement meurent avec le process enfant.

Q3) Quel status final garde le shell pour `cmd1 | cmd2 | cmd3` si `cmd1` échoue mais `cmd3` réussit ?
R: Le code ne retient que le statut du dernier process du pipeline (`wait_all_children` dans `exec_pipe.c`, cas `i == count - 1`), donc le status final suit `cmd3`.

Q4) Que fait exactement Ctrl+C pendant un heredoc dans ton implémentation ?
R: `herydoc_sigint` met `g_exit_status=130`, affiche `^C`, ferme `STDIN`; la lecture heredoc s’arrête, `handle_heredoc` ferme les FDs du pipe heredoc, restaure `stdin` et le handler normal, puis `prepare_heredocs` échoue et la commande est abandonnée.

Q5) `exit 1 2` quitte-t-il le shell ? Et `exit abc` ?
R: `exit 1 2` affiche “too many arguments”, retourne `1` et ne quitte pas; `exit abc` affiche “numeric argument required”, positionne `g_exit_status=2` et retourne `-1` donc la boucle shell quitte via le dispatch d’exécution.
